# Nova documentation comment gaps

Measured against the `v1.0.0.18` tag. This is for the Nova library, not for the
website. It records where XML documentation comments are missing, so the gaps can
be filled at the source rather than guessed at here.

This file is excluded from the Jekyll build and publishes nothing.

## Why it exists

Every API page on the website is written from the library source. Where a member
carries a `<summary>`, the page quotes the author. Where it does not, the page is
written from reading the implementation, which is an outside reading of intent
rather than a statement of it.

Pages built that way carry a visible note saying so. As gaps are filled in Nova,
those pages get revised and the note comes off.

## How it was measured

A scan of every public member in each source file, checking for a `<summary>`, a
`<param>` per parameter, and a `<returns>` on anything that returns a value.

Approximate by design. It reads the declaration and the comment block directly
above it, so it will miss a comment written somewhere unusual, and it does not
judge whether an existing comment is any good. It is meant to point a human at
the gaps.

## Headline

| | |
| --- | --- |
| Public members scanned | 203 |
| Fully documented | 90 (44%) |
| Missing a summary | 113 |
| Missing one or more parameter descriptions | 51 |
| Missing a returns description | 22 |

The distribution is not even. It follows files, which suggests the documented
ones were written at a different time rather than that anyone chose which
members deserved comments.

**Fully documented, nothing needed:** `SpectrumFoundation` (29 of 29),
`PipesConnection` (11 of 11), `PipesServer` (6 of 6).

**Nothing at all:** `SpecDataPoint`, `SpecDataPointEx`, `ChromatDataPoint`,
`Chromatogram`, `TSpectrum`, `Spectrum`, `SpectrumEx`. Every member of every one
of these lacks a summary. They are in `Nova/data/`, alongside
`SpectrumFoundation.cs`, which is complete.

**Partial:** `FileReader` (4 of 17 complete), `ThermoRawReader` (7 of 13),
`MzMLWriter` (1 of 9).

## Where it would help most

Not a severity ranking, and nothing here is a defect. These are the members a
caller reaches for most often, or where the behavior cannot be read off the
signature.

**`FileReader`.** The library's main entry point, and most of it is undocumented.
`ReadSpectrum`, `ReadSpectrumEx`, `ReadChromatogram`, `OpenSpectrumFile` and
`SetFilter` have no summary, no parameter descriptions and no return description
between them. `CheckFile` and `CheckFileFormat`, which a caller touches far less
often, are complete including their exceptions.

**`SpectrumFileReaderFactory.GetReader`.** No comments at all. It is the one
public member of that class, and the documented way to obtain a reader now that
the concrete readers are internal.

**`MzMLWriter`.** Eight of nine members undocumented, and the `Add*` methods take
parameters with no descriptions.

**Read and Write on the data types.** `SpecDataPoint`, `SpecDataPointEx`,
`ChromatDataPoint`, `Chromatogram` and `TSpectrum` all serialize themselves, and
the field order is a format rather than an implementation detail. A signature of
`void Write(BinaryWriter)` does not say what lands in the stream, so the layout
currently has to be read out of the body.

**`PrecursorIon.FramentationMethod`.** Lacks a summary, and is the misspelling
being corrected in 1.1.0.
